Status: plan only. Nothing here has been applied. Source: the database audit of commit `bbe65a9f` (audit ids A1 to E5), re-checked against `docs/`, the migrations and the application code on `origin/phase4-fixups`.

**Verified vs suspected.** VERIFIED means I saw the evidence myself (a file and line, or a read-only SQL result on the local database) and it is quoted. SUSPECTED means the audit claims it, I could not confirm it, and the extra evidence needed is named. Audit claims I did not check are not copied; they appear only under SUSPECTED or in section 5.

- Local database: `kanban-db-1`, 49 rows in `schema_migrations`, so 0050 to 0052 are checked from the files only.

## 1 Executive summary

The schema is a sound multi-tenant base. Composite keys, forced RLS, the definer-function pattern and the append-only audit trigger all check out. Four items need action before real children's data or release of 0050 to 0052; eleven more are important but can follow.

| Count | Items                                                                        |
| ----- | ---------------------------------------------------------------------------- |
| P0    | 4 (A2, A3, A6, A4)                                                           |
| P1    | 11 (A1, A5, A7, A8, A9, A10, A11, A15, B1, B7, E1)                           |
| P2/P3 | the rest (indexes, naming, redundancy clean-up, partitioning); see section 5 |

Most urgent three:

1. **A2** Seat hold capacity can be bypassed by an UPDATE. One small migration closes it, and the app is unaffected.
2. **A3** The session delete in 0052 silently cascades rosters, groups, rooms and form links. Fix before 0052 is released.
3. **A6** Migration 0050 drops session prices it could not copy and only prints a NOTICE. Fix before 0050 runs anywhere that matters.

Audit claims that did not hold up or need softening (details in section 8):

- **D3 (camp delete removes audit rows, "conflicts" with docs): not a conflict.** `docs/phases/00-foundation.md` line 30 says deleting an org must still work.
- **RLS role gaps (A1):** the audit says only `org_members`, invites and `member_calendar_tokens` are role-aware. `orgs_update` is also role-aware (0036, verified in `pg_policies`).
- **A9 (one hold per household):** this is a documented limit in docs 03 and 04, not a hidden bug.
