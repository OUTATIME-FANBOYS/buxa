# Phase 3: registration

Status: **in progress.** Built on the v0.3 phase 3 branch (`v0.3/enhance/phase3-fixups`, migrations 0023 to 0041): sign-up forms and their versions, confirmation, class prices (moved from sessions to classes in migration 0050), seat-hold rules, the teacher role with its class assignments and per-person options, the camp and teacher calendar links, public session pages, and session edit and delete. Taking a hold on the registration, the waitlist UI and price display moved to phases 4 and 6 (see below). Public self-registration by a family is phase 6. Teacher invites by email are built (migration 0038); invites for other roles are not. Roadmap row: "Registration: sign-up forms with custom fields, confirmation. No card payments yet (demo only)." Card payments and refunds moved to phase 9 (`09-payments-go-live.md`).
Depends on: phase 2 (sessions and enrolments).

## What is built (sign-up forms)

- **A form has a name and the sessions it covers.** A staff admin creates a form with a name, the sessions it covers (one or more sessions of the camp) and its own questions. A season is no longer entered: a form written before that keeps its stored season for history, and it is not shown anywhere; new forms and draft saves store a null season. The questions are typed: text, choice (two or more options), date, or yes or no. A form is a draft until it is published.
- **Publishing freezes a version.** Publish writes the draft as the next numbered version. Later edits to the draft do not change it; each registration stores the version it was answered against.
- **The whole form is a draft until it is published (migration `0071_registration_form_drafts.sql`).** Save draft stores the name, sessions and questions as the draft (the season is written as null) (`draft_name`, `draft_season`, `draft_session_ids`, `draft_fields`) and changes nothing families see. Publish copies the draft, in one transaction, into the live name and session rows and into the new version, which also stores the name and sessions it was published with (and the season, null for new forms) (versions before 0071 have none of these, so readers use the live rows for them). Families register on the published version only: its sessions and its name come from the version, never the draft. The Registration page shows the published name and version, with a muted "Unpublished changes" note when the draft differs; the edit pop-up loads the draft, and the View pop-up shows the published version. Attachments are not yet part of the draft: a file saved to a published form is available to families at once (the file rows have no version column).
- **Standard questions** are asked on every form: the camper (first name, last name, date of birth), the parent or guardian (name, email optional, phone), and an emergency contact (name, phone).
- **Taking a registration.** Staff with `registration:submit` record a registration for one or more of the form's sessions, on the published version. One form can cover several sessions, and one family can enrol in several of them. Each registration is recorded with a place for each child and class; the sessions it covers are derived from those classes (`registration_sessions` is no longer written, see "Registration lifecycle"). It is recorded as **pending**. The server checks the answers against that version with zod (the browser is not trusted) and checks the sessions against the form's session set. Nothing is charged.
- **Confirmation** is a separate staff action. Staff, admins and owners (`registration:confirm`) confirm a pending registration from its form's page (Confirm, on each pending row). Confirming sets it to confirmed, with the time and the user, and writes `registration.confirm` in the same transaction. A registration that is already confirmed is refused, so a second confirmation writes nothing. Viewers cannot confirm. There is no un-confirm; a registration can be withdrawn (see "Registration lifecycle").
- **Confirming does not enrol anyone.** A confirmed registration creates no enrolments. Staff add the camper in People, then enrol them in the class (the class page).
- **Confirming issues badges.** In the same transaction as the confirmation, each camper with no active badge gets one (`registration.confirm` and the badge rows commit together). Staff without `credentials:manage` confirm without badges, and are told an admin must issue them. If `BADGE_ENCRYPTION_KEY` is missing, the confirmation fails and rolls back, so the registration stays pending (`docs/deploy.md`).
- **Submissions by session.** The form page lists the registrations for each session, with the answers behind a disclosure.
- **Audit.** `registration_form.create`, `registration_form.update`, `registration_form.publish`, `registration.submit` (a recorded, pending registration) and `registration.confirm` are written in the same transaction as the change.
- **Storage.** Migration `0023_registration_forms.sql`: `registration_forms` (draft), `registration_form_sessions` (the session set), `registration_form_versions` (frozen definitions), `registrations` and `registration_sessions`. Every table has `org_id`, forced row-level security and one policy. The request role has no DELETE; the session set is replaced by `buxa_replace_form_sessions`.
- **Screens.** `/camp/registration` (the forms, then every registration across all sessions in a search list; each row links to its session's Registrations tab), `/camp/registration/new`, `/camp/registration/[formId]` (edit draft, publish, registrations by session) and `/camp/registration/[formId]/register` (take a registration). The sidebar item is under Operations and needs `registration:read`.
- **Registrations inside each session (branch `v0.4/feat/session-tabs`).** A session's page (`/camp/sessions/[id]`) has a Registrations tab (`?tab=registrations`) with the registrations that ask for that session, grouped by form. The rows and the confirm and payment actions are the same ones the form page shows. The tab needs `registration:read`; a viewer or teacher does not see it, and a URL that names it falls back to Classes. The session tab and the Registration list read through `loadFormSubmissions`, which the session tab filters to its session.

**Deviation from the acceptance criteria:** a family does not register by itself yet. A signed-in staff member records it on the family's behalf. A family-facing link needs an anonymous or parent-account entry point, which belongs to the parent portal (phase 6).

**Not built, and the seam for it:**

- Holds and the waitlist moved to phase 4 (Seats & rosters). See `04-seats-rosters.md`, "Moved from phase 3".
- Price display on the registration moved to phase 6 (Comms & extras). See `06-comms-extras.md`, "Moved from phase 3". Prices are stored on each class and shown on the class and public session screens.
- Public self-registration by a family is phase 6 (the parent portal). Registration is staff-only in this phase.

## Sessions, public pages and time zones

- **Edit and delete a session.** Staff, admins and owners (`classes:manage`) edit a session's name, description, dates and public flag. A session has no price (see "Prices" below). A session with no classes is deleted as before. The database refuses a plain delete of a session with classes: migration `0035_session_delete_guard.sql` puts a trigger on `classes` (`classes_refuse_delete_with_classes`), so a delete that would cascade into classes fails even if the app check were missing. A session with classes is offered two choices instead (see "Archive and delete with classes", below).
- **Archive and delete with classes (migration `0052_session_archive_and_delete.sql`, branch `v0.4/feat/session-delete-archive`).** A session with classes opens "Summer 2027 has 2 classes. Archive the session, or delete its classes and the session." Archive (staff and above, `classes:manage`) sets `classes.archived_at`: the session is kept with its classes and history, is hidden from registration (the take-a-registration page does not offer it, and a submission that names it is refused) and from its public page, and shows an "Archived" pill in the list. Unarchive needs `org:update` (admin and owner) and is on the session's Edit dialog. Delete classes and session needs `classes:delete_with_classes` (admin and owner): the person types the session name exactly before the button enables, and the server checks the name too. `buxa_delete_session_with_classes_v1` deletes the classes and then the session in one statement, and refuses (and deletes nothing) when any class has an enrolment, a seat hold, a registration, a check-in or a season pass: "This session has enrolments, archive it instead". Each deleted class writes `class.delete` and the session writes `session.delete`, in the same transaction. The bulk delete and the row trash refuse a session with classes with "Not deleted: <name> (has classes; archive it instead)". Archive and unarchive write `session.archive` and `session.unarchive`.
- **Session lifecycle (migration `0053_session_status.sql`, branch `v0.4/feat/session-lifecycle`).** A session (a row of `classes`) has a status: **draft**, **live** or **archived** (`classes.status`; `archived_at` stays as the time it was archived). New sessions start as drafts. Existing sessions become live, and an already archived one becomes archived (the column is added `NOT NULL DEFAULT 'live'`, so a release that does not know it keeps writing live sessions, and the app writes `draft` itself for a new session).
  - **Draft.** Registration and enrolment are refused: a submission that names a draft session is refused with `session_not_open`, and an enrolment or a seat hold on one of its classes with `session_not_live` ("This session is a draft. Go live before taking registrations or enrolments."). The session list shows a Draft pill. A draft is deleted with everything under it (its classes, groups, rooms, assignments, instructor links and registration-form links) by an admin or the owner (`classes:delete_with_classes`): the confirmation lists what will be removed (`sessionDeleteImpact`) and the person types the session name exactly. `buxa_delete_draft_session_v1` does the delete in one statement and refuses a session that is not a draft. It writes `class.delete` for each class and `session.delete` with the counts, in the same transaction.
  - **Go live.** Admin and owner only (`classes:publish`, a new permission). Go live is in the session's Edit dialog. It sets the status to live and writes `session.publish`. A live session is returned unchanged; an archived one is refused (unarchive it instead).
  - **Live.** Registration and enrolment are accepted; the public page and the take-a-registration picker show it. Deleting is refused until every student is unenrolled and no hold or registration remains (the same refusals as migration 0052): "This session has enrolments, holds or registrations. Unenrol every student first (refunds may be needed), clear the holds and registrations, then delete it. Or archive it instead."
  - **Archived.** Closed and kept. Hidden from registration and the public page, and enrolment and holds are refused. Archive needs `classes:manage`, unarchive needs `org:update` and returns the session to live. The public-page functions and the registration rule check `status = 'live' AND archived_at IS NULL`, so a release that still sets only `archived_at` is respected.
  - **Pills and screens.** The session list shows Draft, Live or Archived beside each name. The Edit dialog states the status and shows Go live (draft, admin and owner) or Unarchive (archived, admin and owner). The take-a-registration picker offers live sessions only.
  - **Tests.** `apps/server/src/classes/sessionLifecycle.test.ts` (in memory), `apps/server/src/registration/PgRegistrationLifecycle.pg.test.ts` and `packages/db/test/session-registration-lifecycle.test.ts` (Postgres), and the upgrade check in `packages/db/test/migration-seed-upgrade.pg.test.ts` (existing sessions become live, an archived one archived).
- **Registration lifecycle (migration `0054_registration_lifecycle.sql`).** A registration has a status of pending, confirmed or **withdrawn**, and can be archived.
  - **Withdraw** (`registration:confirm`: staff, admin, owner). Releases the registration's seat holds and cancels its enrolments through the existing hold and cancel paths (so the waitlist moves up), marks it withdrawn (`withdrawn_at`, `withdrawn_by`) and keeps the record, its answers and its places. A withdrawn registration cannot be confirmed or withdrawn again. Writes `registration.withdraw`.
  - **Archive and unarchive** (`registration:confirm`). Sets `archived_at`. An archived registration is hidden from the lists (the Registrations tab shows it under "Archived registrations", the main list behind "Show archived registrations") and is kept. Writes `registration.archive` or `registration.unarchive`.
  - **Delete** (`registration:delete`: admin and owner only). Erases the registration and all its answers (`buxa_delete_registration_v1` blanks the answers and deletes the row; its places cascade). A confirmed registration that still has enrolments is refused with "Withdraw it first". A registration that was never confirmed has its holds released and its waitlist entries cancelled first, so no place is left behind. Writes `registration.delete` with the form id, the status and the number of places only, no answers or names. The request role still has no direct DELETE.
  - **Screens.** The three actions are on the Registrations tab of a session, on the form page, and on the main registration list (one Withdraw, Archive and, for admin and owner, Delete per row; Withdraw and Delete ask a second time).
  - **A registration's sessions are derived, not stored.** The app no longer writes `registration_sessions`. Readers take a registration's sessions from its places (`registration_classes` to `sessions` to `classes`), so a registration made before places were chosen (which has `registration_sessions` rows and no places) no longer lists its session. The table is kept for now; dropping it is a later migration, after one release has run without it.
- **Session names are unique in a camp.** Compared ignoring case and surrounding or repeated spaces (`sessionNameKey` in `packages/domain`). The create and edit forms show "A session named Summer 2027 already exists." as polite text on the name field. The service checks it, and a unique index on `lower(btrim(regexp_replace(name, '\s+', ' ', 'g')))` per camp enforces it in the database. Migration 0050 checks every camp first: if two sessions already share a name it stops with the list, adds no index and changes no name, so the duplicates are renamed by hand and the migration run again.
- **Session dates and flagged classes (migration `0059_session_dates_flag.sql`, branch `v0.4/feat/session-date-edit`).** A session's dates can be shortened without locking its classes in. A class (a row of `sessions`) whose time range falls outside the session's new first and last day is **flagged**, and keeps its times. The stored flag is `sessions.dates_outside_session` (default false). The flag is kept in step with the dates on every session save, in the same transaction: a flagged class is one whose days are outside its session's days, and a class the dates cover again is cleared.
  - **The rule (one domain check).** `packages/domain/src/classes/sessionDateFlags.ts`: `planSessionDates` plans the flags, `classDatesRefusal` is the check every write path asks, and the copy for the refusals is there too.
  - **Shrink refused when people are on an affected class.** A save that would flag a class with an enrolment, a seat hold or a registration, or in a session with a check-in, is refused with "Swim Stars would fall outside the new dates, and it has people on it. Move or cancel it first, then change the session dates." (several classes are listed by name). Nothing is saved or flagged. A check-in names the session, not a class, so one check-in in the session counts for every class in it.
  - **Audit.** A save that flags classes writes one `class.dates_flagged` entry per newly flagged class, in the same transaction as the session's `session.update`.
  - **Edit session dialog.** When the dates change, the dialog asks the server which classes would be flagged (`previewSessionDates`, read only). If any would be, it lists them ("3 classes fall outside the new dates: Swim Stars, ...") with Confirm and Cancel; Confirm saves, and the toast offers "Fix 3 classes", which opens the session's Classes tab. A change that the server would refuse saves at once, so its reason shows as usual.
  - **Classes tab.** A flagged class shows a "Dates outside session" pill, and the tab has a banner while any class is flagged. A class is fixed by saving it with dates inside the session (`classes:manage`, as before; a teacher cannot change a class's dates). The save clears its flag in the same statement.
  - **What a flagged class blocks.** Until its dates are fixed, a flagged class takes no enrolment, no seat hold and no registration place (the enrolment path, `takeClassPlaceInTx` for a registration, and `placeHoldInTransaction` each refuse it with "This class falls outside its session's dates. Fix its dates first."). The take-a-registration picker does not offer it. Its public page does not list it (`buxa_public_classes_v2`, migration 0059). Its session cannot go live: "This session cannot go live: Swim Stars has dates outside the session. Fix its dates first." A flagged class that is already enrolled cannot exist, because the shrink is refused first.
  - **A class edit outside the session is still refused** in the app with "The class falls outside the session dates. Change the session dates first." Session dates can always be widened, so there is no deadlock. A widening that covers a flagged class clears its flag, because the flag means "outside the dates".
  - **The database trigger (0022, `sessions_widen_session_dates`).** Migration 0059 replaces its function body and keeps the trigger: a write of a flagged class never widens its session (the dates are the owner's to set), and a class inside its session's dates is still a no-op. The trigger is not changed for unflagged classes, so a class written outside its session by a release that still runs the old code widens the session as before.
  - **Permissions.** No change: a session date edit, the preview and a class fix need `classes:manage`, as before. Publish needs `classes:publish`, as before.
  - **Tests.** `packages/domain/src/classes/sessionDateFlags.test.ts` (the rules), `apps/server/src/classes/sessionDateFlags.test.ts` (in memory: flags, refusals, publish, enrol, fix, audit), `apps/server/src/classes/sessionDateFlags.pg.test.ts` (Postgres: the flags, the transaction and audit, the trigger, the public list, publish, enrolment), `apps/server/src/registration/PgRegistrationClasses.pg.test.ts` (a registration for a flagged class is refused with the message and writes nothing).
- **Public flag.** A session is public only when staff tick "Public" in New session or Edit session. The session page has no toggle in this phase.
- **Public session pages** (migration `0029_public_sessions.sql`, `/camps/[slug]/sessions/[sessionId]`). Read without signing in. They list the session's upcoming classes and show no contact details and no enrolled campers. Off by default.
- **Time zones.** Class times are typed and shown in the user's own local zone and stored as UTC instants. The day-boundary rules (a class must fall on days inside its session) and the weekly series are worked out in the camp's time zone.

## Teachers and invites

- **The teacher access level is retired (migration `0069`).** It was a membership role (`org_members.role = 'teacher'`, migration `0026`). Every teacher login is now viewer access, and its person holds the **instructor** person role; the teaching view is that combination. The rules are in `docs/ROLES.md`, and the role keys and labels are defined once in `packages/domain/src/roles/roles.ts`. The six person roles (camper, participant, guardian, instructor, organizer, admin_staff) describe people, not access.
- **Teacher calendar link** (migration `0033_teacher_calendar_tokens.sql`). Each teacher can make one personal link from Settings. It shows only the classes the teacher is assigned to. The camp link (migration `0028`) is unchanged, and it stays with admins and owners. Making a new link stops the old URL working at once.
- **One source for a class's teachers (migration `0051`).** A teacher is assigned to a class by making its roster person an instructor of the class (`session_instructors`, the same list the Edit class popup saves). The Teachers section on the session page is gone. A teacher's login is linked to its roster person (`people.user_id`): on invite accept, the person with the invited email in that camp is linked (or created with the instructor role when none exists). The teacher's classes, its My classes page, its personal calendar feed and the audit notices all read through that link. `class_teachers` (migration `0027`) is no longer read or written by the app. Migration `0051` moves existing rows across by email (case and spaces ignored) where the match is unambiguous; a row with no matching person is reported in the migration log and keeps `class_teachers` until the owner has reviewed it.
- **Teacher invites by email** (migration `0038`, table `member_invites`). Staff, admins and owners add a person with the Instructor role on Add person, enter the email and send the invite. The link is shown once and expires after 7 days. The invited person opens it, signs in with the same email, confirms their profile and joins with viewer access and the instructor role. Only a hash of the token is stored; sending again replaces the token, so the old link stops working. Pending invites to a person's email are removed when that person is deleted. Invites for the other roles show "Invites for this role are coming soon." Sign-up confirmation is not working end to end yet, so a new account may not be able to finish; see `docs/auth.md`.
- **Notifications** (migration `0037`) are one row per recipient, written from audit actions by the rules in `apps/server/src/notifications/rules.ts`. They are not invitations.

## People, team access and the camp switcher

- **People list pages.** The list shows 25 people a page, and a page can ask for up to 100. Search and the role filter are applied before paging, so the count and the page numbers match the filter. The page is in the address, so Back works (`packages/domain/src/people/paging.ts`).
- **One person form.** Add person and Edit person open the same pop-up (`PersonForm`). Roles are checkboxes in two groups: Family (camper, guardian) and Staff and participants (the rest). Only the ten role sets in `packages/domain/src/people/roleCombinations.ts` are saved; the form and the server refuse any other combination. A staff role is held one at a time, except that a guardian may also hold instructor, organizer or participant, and a camper may also hold participant.
- **Email.** One email per person, stored in `people.email`. The field is labelled Household email when a family role is ticked, and Email otherwise. The invite button stays disabled until the email is a valid address.
- **Household section.** Shown for a camper, or a guardian. On Add it links the person to a household. On Edit it shows the current household, but the household fields (the household and the relationship) are not saved on edit yet. The email and roles are saved.
- **Person page.** `/camp/people/[id]` shows four tiles in a two-column grid (one column on a narrow screen): Membership and Household on the first row, Badge and Attendance on the second. The Details card is gone. The email sits under the name, and Edit details and Archive person are in the header. Archive person needs `people:delete` and is hidden for an archived person.
- **Gap: date of birth and phone are not on the person page.** The server sends them to staff, and a `ContactDetails` component exists, but the page does not render it. To fix before real data.
- **Badge panel.** Admins and owners get Show badge, Reprint, Reissue and Revoke when a badge is active, and Issue badge when none is. Show and Reprint display the code; Reprint keeps the same code for a damaged card. Reissue makes a new code and revokes the old one, and shows "Badge reissued." with no code. Revoke shows "Badge revoked." and Issue shows "Badge issued.". Staff see the panel with a note that only admins can issue or revoke badges. The code is not in the page's props.
- **Staff hierarchy (confirmed by the owner):** admin staff, then organizer, instructor and participant, highest first. Each person holds one staff role (`STAFF_ROLE_ORDER` in `roleCombinations.ts`).
- **Delete a person (owner only).** The owner gets a Delete button on each row, and a checkbox per row with select-all and Delete selected for a bulk delete. Both open a confirm dialog with an explicit Delete button. The delete removes the person's memberships, enrolments, check-ins, badges, instructor rows and household links, and the pending teacher invites to that email. It writes `person.delete` with no personal details. Archiving is a different action, open to admins and above (`people:delete`), and it keeps the record.
- **Manage access.** Admins and owners open Manage access from Team access to change each member's role, one row at a time. Nobody changes their own role. Only the owner makes or removes an owner, and the camp keeps at least one owner. Each change writes `member.role_change` with the old and new role (migration `0039`).
- **Team access expiry.** Manage access also sets an optional "Expires on" day for each member, and "Clear expiry" removes it (migration `0043`). The day is the start of that day in UTC, and from then the person has no access to the camp: the server refuses it everywhere, including the sign-in list, and the Team access list shows an "Expired" pill. An expiry within 14 days shows "Expires <date>" on the Team access list. The rules are the role rules: an admin or owner, never oneself, only an owner changes an owner's expiry. Each change writes `member.expiry_set` or `member.expiry_clear`. Season-pass expiry is separate and unchanged.
- **Camp switcher.** The camp name in the top bar opens a searchable list. Without a search it shows the eight most recent camps, and a search covers every camp. The list scrolls under a maximum height (half the window, at most 360px). Archived camps sit behind "Show archived", one row per camp. The switcher only switches camps. Rename, archive and delete are in Settings: a camp name card (rename, for admins and the owner) and the Danger zone (archive, for admins and the owner; delete, for the owner only).

## Moved from phase 2: recurring events, public class pages and the iCal feed

These were in the phase 2 roadmap row and moved here so that phase 2 closes on classes, sessions and enrolment alone.

- **Recurring sessions:** a weekly rule expands into normal sessions, each with its own enrolments. Overlap and capacity still apply to each. Tests cover month ends, DST days, and the count and until limits.
- **Public class pages:** a read-only page per class, listing its upcoming sessions, with no contact details and no enrolled campers. Only classes marked public.
- **iCal feed:** a read-only feed per camp that calendar apps subscribe to by URL, authenticated by an unguessable token stored as a hash. Archived camps return not found.

**Built** on the phase 3 branch: migrations 0028 (camp calendar token) and 0029 (public sessions). The earlier attempt used 0020 and 0021, which clash with shipped migrations, so the numbers were moved to 0028 and 0029.

Terms: a **session** (the parent row) is the public page's unit, and its **classes** are the time ranges a series generates. A public page lists a session's upcoming classes.

- **Recurring series:** staff add a series to a session from its page (`RecurringSeriesButton`, `addRecurringClasses`).
- **Making a session public:** the Public tick in New session and Edit session (see "Sessions, public pages and time zones").
- **Camp calendar link:** admins and owners make it in Settings (`CalendarLinkCard`, `rotateToken`). Making a new one stops the old URL working at once. Staff and teachers do not see the camp link.
- **Open:** the token is in the feed URL's query string. Calendar apps cannot send headers, so the token has to be in the URL. The remaining risk is platform request logs; check their retention.

## Prices (per class; migration `0050_class_prices.sql`)

- **A price belongs to a class, not a session.** A session (a row of `classes`) carries no price. Each class (a row of `sessions`) carries its own price, and a family pays per class. Stored as integer minor units with an ISO 4217 code, plus an optional early-bird amount and its last day, with the same shape check as before (the early bird is not above the price, and the amount and day come together). Nothing is charged.
- **Moving the price.** Migration 0050 adds the price columns to `sessions`, copies each session's price onto each of its classes (a class that already has its own price keeps it), then drops the price columns from `classes` (the drop is approved in the file). A session with a price and no classes has nowhere to copy it to; the migration prints a notice with the count. The earlier migration `0024_session_prices.sql` is unchanged. The public class list reads through the new function `buxa_public_classes_v2` (the 0029 function keeps its return type for the release still running).
- **Early-bird rule:** the early-bird amount is shown while today, as a calendar day in the camp's time zone, is on or before the early-bird last day. From the next day, the regular price is shown. Tested in `packages/domain/test/session-prices.test.ts` (boundary day, 23:30 in the camp zone, and the day after).
- **Rounding:** amounts are integers, and typed input is never rounded. Extra decimal places are refused (`parseMoney`). Formatting uses integer arithmetic only.
- **Input.** The class form (and the recurring series form) takes the price, the currency and an optional early-bird discount, which the form turns into the early-bird amount. The session form and the session input take no price: `NewSessionInputSchema` is strict, so a price sent with a session is refused.
- **Who:** staff and above (`classes:manage`) set a class's price. A viewer is refused by the service. A teacher may not change a class's price (it is one of the locked fields, `teacher_field_refused`).
- **Audit:** a change to a class's price writes `class.price_change` with the previous and new price (minor units), in the same transaction as the class write. An unchanged price writes nothing. A class created with a price writes one entry. The old `session.price_change` action stays in the list because earlier audit rows use it.
- **Screens:** the session form has no price field and the session page shows none. The class list has a Price column, and the selected class's details show its price for today. The public session page shows each class's price beside its ages.
- **Seed:** `scripts/seed-mock` gives each planned class its price (one class has none). A re-run brings an existing class's price to the plan and changes nothing else.
- **Not yet:** multi-currency conversion is out of scope.

## Status: seat holds

**Built (branch `v0.3/feat/seat-holds`):**

- A hold reserves one place in a class for a child, recorded with the child's household (`seat_holds.person_id`, migration 0055). One active hold per child per class (a unique index on `(session_id, person_id)` while unreleased); two siblings of one household each hold their own place. It counts as taken only while it is unreleased and its time has not passed, so an expired hold returns its place at once, without a job.
- The default length is one constant, `SEAT_HOLD_MINUTES` (15) in `packages/domain/src/classes/holds.ts`. A camp may set its own length, from 5 to 60 minutes (see the registration phase, below).
- Capacity holds under concurrency: the hold and enrolment triggers (migration 0025) lock the class row and count enrolments plus live holds. Tested on real Postgres with parallel holds and holds racing enrolments for the last place.
- A place freed by a cancelled hold, an expired hold or a cancelled enrolment goes to the first waitlisted enrolment, in the order they joined. Each promotion is audited (`enrolment.promote`). Waitlist promotion was not in phase 2.
- The cleanup (`releaseExpiredHolds(orgId)`) releases expired holds and promotes waitlists. It is safe to run twice. Enrolling a camper and placing a hold first free the class's expired holds, so the waitlist is never skipped.
- Permission `holds:manage` (staff, admin, owner; not viewer). Archived camps are read-only, as for every write.
- Row-level security and a camp-isolation test on `seat_holds`.
- The `completed` release reason is in the table (migration 0043). Nothing sets it yet.
- The scheduled job for `releaseExpiredHolds`: `GET /api/cron/release-expired-holds`, guarded by `CRON_SECRET`, with the Vercel entry in `docs/deploy.md`. Tests refuse the call without the secret and check that the cleanup frees expired holds in every camp.
- Concurrency and expiry tests for holds: in memory (`seatHoldCapacity.test.ts`) and in Postgres (`seatHoldExpiry.pg.test.ts`).

**Built since, on classes (see the decision in the registration phase):** a registration takes a hold for each child and class (`registration_classes`), a full class waitlists the child in order, confirmation turns each hold into an enrolment, and the class page shows the holds and the waitlist with a promote button.

**Not built yet:**

- Hold length set per camp: built, see the registration phase ("Hold length per camp").
- A hold per child: built in migration 0055 (siblings each hold a place in the same class; one child cannot hold a class twice). A released hold is final: a guard trigger refuses any change to `released_at`, `release_reason`, the class, household, child or expiry, and the request role may update only `released_at` and `release_reason`. Holds released before 0055 may have no child (`person_id` null); new holds must name one.

## Words we use

- **Registration**: a family's request to enrol a camper in one or more sessions, with the form answers and a payment.
- **Registration form**: a camp's form for the sessions it covers, with standard fields (camper, guardian, emergency contact) and custom fields the camp defines. Custom fields are typed (text, choice, date, yes/no) and validated by schema.
- **Hold**: a short reservation of a session place while a family completes payment. A hold expires after a set time (proposed: 15 minutes) and returns the place.
- **Waitlist**: an ordered queue for a full session. A place released by a cancellation goes to the first waitlisted registration.
- **Price**: an amount shown for a class, with an optional early-bird date. Each class has its own price. Shown for information only in this phase; nothing is charged.

## Decisions

1. **No money in this phase.** Registrations are demo-only and no card is charged. Payments follow in phase 9.
2. **Holds, not overselling.** Taking a place is done in a database transaction that locks the session row. A hold expires on its own; a background job releases expired holds.
3. **Confirmation** is a staff action in this phase, recorded in the audit log, until payments arrive in phase 9.
4. **Custom fields are versioned.** A change to a form does not change answers already given; each answer stores the form version.
5. **Prices are stored in the smallest currency unit** with the currency code, for display only.

## Acceptance criteria

- A camp admin can create a registration form for its sessions, add custom fields, and publish it.
- A family can register a camper for one or more sessions and see a confirmation (no payment in this phase).
- A full session takes a waitlist entry; when a place frees, the first waitlisted registration is offered it.
- An unpaid hold returns its place after the expiry time.
- Every registration, confirmation and price change is in the audit log.

## Exit tests (must pass in CI before the phase is done)

- Concurrency: two registrations for the last place, in parallel, produce exactly one confirmed registration and one waitlist entry.
- Concurrency: a hold and a new registration racing for the same place never both succeed.
- Privacy: registration answers are never returned to viewers beyond their role.

## Not in this phase

Card payments, refunds, Stripe Connect, instalments, sponsorship funds (all phase 9). Multi-currency.

### Teaching view (instructor with viewer access)

Organization access is owner, admin, staff and viewer (`docs/ROLES.md`). Teaching is the instructor person role. A viewer whose person holds it is in the teaching view, for the adults who run a class. Its default grants (the same list the retired teacher level had, unchanged):

- `attendance:read`, limited to the sessions of the classes the teacher is assigned to.
- `events:read` and the people in those classes, so it can look up campers. Read-only, limited to the same classes.
- `events:update_details`: change the name of its own classes. A teacher may not change a class's camp size, ages, times, location, price or instructors (the server refuses the change with `teacher_field_refused`). Staff, admin and owner keep `events:update` for every field.
- No contact details, no edits to people or classes beyond the name, no team or admin rights, no money rights.

**Per-person options.** An admin (or owner) turns these on for one teacher on the Team page. Each option is off by default and grants only the one action it names, only in the teaching view, and only inside its assigned classes. The options are listed in `MEMBER_OPTIONS` (`packages/domain/src/permissions.ts`) and stored in `member_options` (migration 0030).

- `teacher.check_in_out`: check campers in and out (`attendance:record`) in its assigned classes. Off by default; without it a teacher is refused check-in and check-out.

`authorize()` is the one decision point. The option is read into the actor for the request (`withMemberOptions`), and the assigned-classes scope is applied on top of it.

**Teacher view: My classes (branch `v0.3/feat/teacher-sessions`).** A teaching view's sidebar has a "My classes" item, shown in the teaching view only, at `/camp/my-classes`. The page is read only. It lists the classes the signed-in teacher is assigned to (the classes whose instructors include its linked person, migration `0051`), grouped by session: the session name and its dates, then each class with its start and end time in camp time (the camp's clock setting), its age range and its location. With no assignments it says "You are not assigned to any classes yet." The page is not found for every other role, and it shows no board, no tasks, no seat counts, no campers and no instructors. The server reads the classes through the same assigned-classes scope as the Sessions page (`listMyClasses` in `ClassService`, `teacherScopeOf`), so another teacher's classes are never loaded. No migration was needed.

## Decided: families register for classes (owner, 2026)

**Built (branch `v0.3/feat/class-registration`, migration `0046_registration_classes.sql`).**

- **Data.** `registration_classes` holds one row per child and class of a registration: the hold taken for it (`hold_id`), the waitlist or enrolment it became (`enrolment_id`), and its payment (`payment_status`, default `unpaid`, with a note, `paid_at` and `paid_by`). It has the same tenant rules as the other registration tables: `org_id`, forced row-level security, composite foreign keys, and no DELETE for the request role.
- **Form.** Staff with `registration:submit` choose the children (people with the camper role) and then the classes of each child, grouped by session. Each class shows its ages, time, and places left (or Full, waitlist). The session is taken from the class. A class that overlaps another chosen class for the same child is refused in place, with a short note; the server checks the same rule and names both classes.
- **Hold length per camp.** Built (branch `v0.4/feat/hold-length-per-camp`, migration 0047). The camp settings page has a "Seat hold length (minutes)" field for admins and the owner: 5 to 60 minutes, or empty for the default of 15 (`SEAT_HOLD_MINUTES`). A hold placed after a change takes the new length; a hold already placed keeps its time.
- **Submit.** Each place that is free is held for the child (recorded with their household) for the camp's hold length (15 minutes unless the camp sets another, `SEAT_HOLD_MINUTES` the default; the existing hold service and capacity trigger). A full class puts the child on that class's waitlist, in the order they joined (a waitlisted enrolment, so the existing promotion path applies). A child with no household cannot take a hold, and the form says so.
- **Confirm.** Confirming a registration releases each held place as `completed` and creates its enrolment through the existing enrolment path and capacity rule (one enrolment per held class). A hold that ran out before confirmation is taken again: the child gets a place if one is free, or the waitlist. Waitlisted places stay waitlisted.
- **Waitlist.** A freed place goes to the first waitlisted child (the existing `enrolment.promote` audit). On the class page, staff see the held places and the waitlist in order, and can move the next camper off the waitlist when a place is free.
- **Payment.** Staff with `registration:confirm` mark each child's place paid by hand. A place marked paid needs a note saying how. The audit entry (`registration.payment`) records whether there is a note, not its text.
- **Staff screens.** Each registration lists its places with the child, the class, the status (held, waitlisted, enrolled, hold expired, cancelled) and the payment.

**Not built, and where it goes:**

- **Online payment and refunds:** phase 9 (`09-payments-go-live.md`). Until then payment is recorded by hand.
- **Packages** (several classes at a discount): not built. A package would be a second way to group the classes of one registration and one payment; the payment rows are per class, so a package can add a parent row later without changing them. Leave it until the owner picks the rule.
- **Parent logins and family self-registration:** phase 6. Staff still enter the registration.
- **One hold per child per class.** Migration 0055 moves the hold rule from the household to the child, so siblings of one household can each take the same class at the same time. The same child cannot take a class twice: the form refuses it with "This child already holds a place in that class." The hold still records the household (the first by id when the child is in several).
- **Price at submission.** Each registration place keeps the price the family saw: `price_minor`, `price_currency` and `early_bird_applied` on `registration_classes` (null on places made before migration 0055 and for a class with no price). The amount is the early-bird amount while its date has not passed, in the camp's time zone. Later price changes do not touch it. Staff see it beside each place on the registrations screen.
- **Registration keys.** A place's enrolment and its hold are each linked by at most one place (partial unique indexes), and a form's `published_version` must name a real version (composite foreign key, null while unpublished). Each migration checks for existing duplicates first and stops with a list instead of changing data.
- **Emails and names.** A person's email is stored in lower case and is unique in a camp (migration 0056; the migration stops and lists the people if two share one). Session, group and room names are stored normalised (NFKC, non-breaking, zero-width and ideographic spaces become one space) and compared that way, so look-alike names clash with the usual "already exists" message.
- **The camper answers are still typed** (first name, last name, date of birth) next to the child picker, because the stored answers and the badge match still use them. Retiring them is a follow-up once the picker is the only source.
- **Browser check:** the form's in-place clash note and the holds panel have server-rendered tests only. They are not checked in a browser yet.

- A **session** is the period (for example "Summer 2027", or a one-week winter camp). A session with one class is still a session with one class.
- A **class** is what a family registers for and pays for. Seats, holds and the waitlist sit on classes.
- A parent registers a child for one or more classes. The child is placed in the session through the class, so nothing extra is entered.
- A child may take more than one class in the same session, as long as the times do not overlap. Overlap is blocked at registration.
- Payment is per class. A camp may also sell a package covering several classes at a discount.
- Confirmation creates the enrolment in each class, and a waitlisted family moves up when a seat frees.

## Class series: who is enrolled, and per day (v0.4, in progress)

See `04-seats-rosters.md`, "Class series and occurrences", for the model and the status. In short, for the series that is being built:

- **Per series:** the enrolment (one per child), the seat holds (one per child), the waitlist, the camp size (capacity), the price, the registration places, and the overlap rule (a child may not be enrolled in two series whose active days overlap).
- **Per occurrence (a day):** its date and time, its status (active or cancelled, with a reason), and attendance. A cancelled day does not change the series or the places.
- Built so far: the database model and migrations 0060 and 0061, the domain rules and cancel and restore on the server. The registration form, the pickers and the New class dialog still work per occurrence until the UI moves (see the 04 document).
